# 设置可靠性审查与实现

日期：2026-09-13。范围：全局 settings.json、模型迁移、主密钥、设置 IPC、导入导出、设置页面自动保存，以及 projects.json 中的项目模型/插件/安全配置写入。

这是基于源代码和隔离测试的审查，没有读取、导出或修改真实用户配置和真实 API Key。下面的问题是已确认的代码路径；没有生产日志，不能将某一次用户遇到的故障唯一归因于其中一条。

## 保存与恢复机制

- settings.json 保持 JSON 兼容，增加 schemaVersion、UUID revision、SHA-256 完整性校验。旧文件允许读取，新版未知 schema 拒绝读取和回写。
- 保存必须在事务内读取当前配置，通过结构校验、解密和版本比较，再合并修改。后台 patch 也在同一队列内执行。
- 写入同目录唯一临时文件，权限 0600，文件 fsync 后原子 rename，再同步目录。加密失败不会开始配置文件修改。
- 覆盖前保存旧版本；成功后保留新版本的独立快照，包括第一次保存。历史位于 settings.json.history，项目配置历史位于 projects.json.history。
- 恢复先尝试主文件；JSON/结构/校验失败时尝试历史，再尝试旧 .bak。解密失败不自动回滚到另一个密钥版本。
- 恢复操作本身也是一次新提交，不直接删除历史。历史当前不自动清理，避免静默删掉最后可用版本；长期使用会占用磁盘空间，应定期导出并由用户决定归档。
- 快照与主文件在同一磁盘，不能替代异机备份。主密钥缺失后，本地密文历史也不能单独解密；可用口令加密的便携备份恢复。
- 文件系统/磁盘/同步调用失败会报错。原子替换已经发生、但目录同步失败时属于提交结果不确定；重新加载确认版本，不应盲目重试覆盖。
- 同一个 userData 仅允许一个新版 Sage 主进程，多窗口仍受支持。旧版进程、外部程序直接改文件不在该锁的保护范围内。

## 导出、导入的产品语义

入口：设置 → 通用 → 配置备份与恢复。配置无法加载时，加载失败页面也提供备份恢复入口。

整份便携文件使用口令派生密钥（scrypt N=32768/r=8/p=1），AES-256-GCM，随机 salt、nonce 和认证标签。格式及算法固定，不接受导入文件自定义昂贵 KDF 参数。口令至少 12 字符，不保存到设置、localStorage 或日志。导入大小限制 10 MiB。

保护勾选项与文件口令是两层不同含义：

| 导出选项 | 导入后设置页 | 系统使用 |
| --- | --- | --- |
| API Key 保护勾选 | 不返回原文，不能查看/复制；同时锁定 Host | 主进程正常解析实际凭证 |
| 仅 API Host 保护勾选 | Host 不返回原文；Key 可查看 | 主进程使用真实 Host |
| 字段未勾选 | 原文正常查看和编辑 | 正常使用 |

保护逐提供商、逐字段保存；之后手工新建提供商不会继承其他提供商的限制。已受保护字段再次导出、合并或恢复历史不会解除其策略。修改受保护 Key 的 Host 被拒绝，避免把现有 Key 发给用户改成的接收服务器；需要替换凭证时新建提供商。

导入先完整验证口令、认证标签和数据结构，才展示确认内容。默认合并保留同 ID 的现有提供商，增加新 ID，并覆盖备份中存在的其他全局设置；明确选择替换才替换整份全局设置。所有提交先留历史。完全无法读取当前配置时，只允许显式替换恢复，恢复的敏感字段保守设为受保护。

导出不会覆盖同名文件：先写完整临时文件，再独占发布。文件名默认带时间。错误口令、篡改、未知格式、无效字段、同名导出、取消操作都不会替换已有配置或备份。

导出范围仅为全局设置；不包括项目内容、对话、记忆或项目安全策略。后者仍保存在各自存储位置。

**保密边界：这是可信应用中的“仅可使用”策略，不是对本机管理员的密码学访问隔离。接收者持有口令或控制应用进程，仍可通过自行解密备份、修改客户端或调试进程提取凭证；Host 也可能通过网络观测推断。若必须让接收方永远拿不到原 Key，成熟方案是服务端代理保管 Key，为接收方签发受限、可撤销的调用令牌。**

## 自动保存

全局保存/取消栏已移除。开关、选择和输入事件提交最小字段更新；输入时若已有保存请求在途，合并后续同字段修改，最终值继续保存。没有关闭页面才触发的防抖计时器。

保存队列独立于 tab 生命周期，切换页面不会取消在途请求或丢掉失败草稿。写盘失败显示错误并保留输入，可重试；多窗口版本冲突不会静默覆盖，需保留输入或确认放弃后重新加载。设置未保存时关闭窗口会提醒。

项目模型、插件也在各自操作内提交；记忆编辑、安全策略等独立流程保留自己的保存/确认按钮。自动保存失败不会因为辅助 CLI 状态检测失败而误报已经成功提交的数据。

## 业界机制与选择

版本历史解决回滚与误操作，事务解决并发和中途失败，校验和解决偶发损坏检测，独立备份解决磁盘丢失，密钥管理解决密文可恢复性。这几种机制需要组合；仅把 JSON 放进 Git 不能保证写入事务或密钥安全，也可能长期保留曾误提交的明文。

SQLite 的事务、journal、同步协议是更成熟的多记录持久化基础；如果后续要统一项目、设置、计划任务及记忆，应采用有迁移、备份 API、完整性检查的 SQLite 存储层。本次保持现有 JSON 路径，降低一次性数据迁移风险，并直接堵住已找到的丢失路径。SQLite 在线备份也应使用官方备份机制，不能简单复制正在写入的数据库。

参考资料：

- [SQLite Atomic Commit](https://www.sqlite.org/atomiccommit.html)：原子提交、恢复日志与同步边界。
- [SQLite Transaction](https://www.sqlite.org/lang_transaction.html)：写事务与并发冲突。
- [SQLite Backup API](https://www.sqlite.org/backup.html)：一致性备份。
- [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)：AES、认证加密及密钥存储。
- [OWASP Key Management](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html)：密钥生命周期、恢复与保护。
- [Electron safeStorage 实现文档](https://github.com/electron/electron/blob/main/docs/api/safe-storage.md)：操作系统后端与安全语义差异。
